## Continuity and benefits

- Upstream requirement：[核心流程](CORE_JOB_WORKFLOW.md)要求 GPT 每日处理两邮箱，Workspace 保存结果，网页查看同一数据库。用户希望保留 ChatGPT 上下文，并询问能否由后台维护扫描回执。
- Current package：记录职责调整、运行完整性要求、权限边界和验收标准，并更新项目入口文档。本轮只交付文档，不修改运行代码、数据库、连接权限、任务配置或部署。
- Downstream enablement：下一轮可据此设计运行身份、工具输入输出、事务和兼容迁移，再实施隔离测试；实际 ChatGPT 平台授权与定时验收仍是独立条件。
- Short-term benefits：明确局部证据写入成功与每日扫描成功的区别，避免把未实现方案当作可用入口。
- Long-term benefits：预期减少 GPT 手动维护进度的调用，使中断后的继续处理及网页时效展示依赖持久化记录；效果需通过实现和真实运行验证。

## 目标职责

| 职责 | 目标行为 |
| --- | --- |
| GPT | 在原 ChatGPT 工作方式下读取邮件、判断相关性、匹配申请、提交获授权的事实与处理结果；保留证据与生命周期规则 |
| Workspace 后台 | 在获授权的扫描开始时建立运行记录，固定范围和截止时间，保存分页、待处理项及结果关联，并据此汇总回执 |
| 数据库 | 保存运行、来源处理进度、相关结构化事实和业务记录，作为唯一持久化依据 |
| 网页 | 读取结果及实际覆盖；保留明确触发的已有申请补查，页面刷新只读取数据库 |

本需求不选择新的调度器或模型 API，不要求迁移 ChatGPT 上下文，也不承诺平台会向
某个任务提供额外聊天历史。已有每日 08:00 Australia/Sydney 目标、最多七天回看及
正常 24 小时重叠窗口继续保留。网页补查不唤醒 ChatGPT 定时任务。

## 运行与处理要求

1. **明确开始。** 扫描必须由获授权的操作启动。后台在来源获取之前持久化运行身份、
   工作区、触发来源、授权依据、两邮箱绑定、查询范围及固定截止时间。具体工具名称、
   请求字段和接口组合留待契约设计，不能把普通读取请求隐式当作用户授权。
2. **身份和重试。** 区分同一次执行重试与新执行；开始重试不重复建立运行。并发执行
   不串用来源处理记录或业务写入。运行与实际批次、来源及写入结果建立显式关联，
   不能仅根据创建时间落在某个区间内就推断归属于该次运行。
3. **及时持久化。** 保存分页位置、待处理项、实际正文读取是否完整、GPT 提交的分类、
   来源证据及必要业务操作结果。新执行继续七天范围内的未完成工作；更早的待处理项
   明确排除，不声称已扫描。已验证处理的来源在重叠窗口和重试中复用。
4. **完整性有证据。** 后台不能仅凭“读过邮件”“保存过一条证据”或“没有新增申请”
   判断完成。无关邮件也需要明确的处理结果；相关邮件需要来源可读、匹配明确、所需
   写入及读取核对完成。GPT 的语义判断仍是模型判断，服务校验不等于独立证明其正确。
5. **自动汇总。** 后台依据持久化处理记录计算新增数量和完成情况，减少 GPT 手工填写
   汇总及开始/结束回执的职责。分页未穷尽、正文不完整、匹配不明、必要写入失败或
   未确认的处理项均阻止相应范围完成。排除广告、已有证据及重放不能计为新增。
6. **中断和恢复。** 定义活动运行的存活、超时、并发及迟到结果处理规则。中断、服务
   重启或超时保留已保存进度，并呈现未完成；不能因超时、停止调用或写了部分证据就
   标成成功。恢复时不得修改已完成回执的原始归属或重复计数。
7. **真实覆盖。** 两邮箱分别计算范围与失败；完成回执和成功 checkpoint 原子提交，
   覆盖单调且不留未解释的缺口。全部所需范围及业务处理通过才显示完整每日扫描。
   单申请补查和本次局部手动证据验证不能推进全邮箱每日 checkpoint。
8. **精简展示。** 维持简洁折叠状态卡，默认显示检查时间、完整/部分/失败及变化摘要；
   展开查看范围与诊断。刷新时间与邮件实际检查时间分开。

## 权限、数据与兼容

- 任何会保存运行日志、批次或处理确认的工具都必须明确披露写入行为，使用准确的
  写工具元数据及实际身份授权；不得把写入藏进只读工具、换名重放被拒请求或直接改库。
- 本方案是职责设计，不是平台拦截修复证明。新的合法工具流程仍需实际环境的授权和
  接受；若被拒，保留失败证据并停止对应操作，不另换通道执行同一被拒写入。
- 保留账户绑定、跨工作区隔离、稳定来源 externalId、幂等去重、生命周期及待办规则。
  后台日志能力不增加业务修改权限，也不扩大网页补查权限。
- Gmail 保持只读；旧 Sheet 保持只读。数据库仅存必要结构化事实和最小来源信息，
  不保存整封正文、签名、附件、凭据或无关私人内容。公开交接文档不复制真实邮件内容。
- 保留历史回执、覆盖和旧记录，不倒填开始时间、不补造完整回执。先定义新旧调用的
  兼容期和运行版本归属；新增迁移如有必要须通过副本升级、重复启动与回退验证。
- 当前 start/finish/next/ack 与已保存任务提示词仍按现有契约工作。新流程部署且工具
  发现可用后再同步提示词，不能提前指示现有任务调用不存在的接口。

## 实施顺序与验收

先完成契约设计，再实现服务、工具和隔离测试；发布前准备可审阅的迁移、兼容与回退
结果。真实手动验收和定时验收分别记录；GitHub 推送不等于部署或启用任务。

| 验收场景 | 必须证明 |
| --- | --- |
| 开始与重试 | 身份及授权可校验，重试复用同一运行，新执行不冒充旧执行 |
| 同时运行 | 结果归属准确，不重复记账、不串工作区；重复来源依规则复用 |
| 中断及重启 | 已保存进度保留，从待处理项继续；超时与迟到结果不伪造完成 |
| 来源完整性 | 未穷尽分页、不完整正文、账户换绑、未确认分类及失败业务操作阻止完成 |
| 合法零更新 | 两邮箱处理完整且无变化可真实完成；未读完的零写入不能完成 |
| 业务一致性 | 广告排除，真实证据保留，幂等重放不计新增，必要状态/任务写入失败可追踪 |
| 原子性与兼容 | 回执和覆盖同事务，失败不推进，旧数据保留，新旧运行归属明确 |
| 入口与展示 | 网页刷新不取邮件；申请补查不算全邮箱覆盖；摘要与详细记录一致 |
| 平台手动验收 | 在实际 ChatGPT 任务环境通过真实授权、工具调用及持久化读取核对 |
| 实际定时验收 | 独立验证真实定时触发、两邮箱处理及回执；不能用 Codex 手动结果代替 |
