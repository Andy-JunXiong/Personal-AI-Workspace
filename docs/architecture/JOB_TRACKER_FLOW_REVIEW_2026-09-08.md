## Continuity and benefits

- Upstream requirement：用户确认每日 GPT 查邮件并保存结构化结果，网页主要查看同一数据库，下午有新邮件时可手动补查。延续 [核心流程](CORE_JOB_WORKFLOW.md)。
- Current package：核对现有网页、Gmail、MCP、入库及扫描进度代码，区分已经符合的设计和需要统一的处理规则。本次只更新评估与文档。
- Downstream enablement：下一步可实现共用邮件标识与去重，再定义按需增量补查；完整定时验收仍取决于解决当前平台调用问题。
- Short-term benefits：已确认无需重建数据库或增加网站与数据库之间的同步层；发现跨入口邮件标识不一致、手动检查范围与进度口径不同。
- Long-term benefits：两种触发入口可持续维护同一份可信数据，重复执行不重复新增，页面清楚说明数据时效。该效果仍需实现与验收。

## 产品关系

```text
每日定时入口 ──┐
              ├─ 邮件获取 → GPT 提取信息 → 后台校验、去重、保存 → 同一数据库
网页手动补查 ──┘                                                ↓
                                                       网页读取、展示
```

这是目标职责划分，并不表示当前两条路径已经共用完整处理实现。
网页打开、筛选、刷新已保存结果不应触发邮件获取或模型调用；明确的补查按钮才启动检查。
网页操作少不等于一次补查工作量一定小，应限制后台查阅范围并复用已处理结果。
Gmail 保留原始邮件；数据库保存相关结构化事实、来源、证据摘要、申请和待办等记录，
不因“抓取原始数据”而自动扩大为全邮箱正文或附件归档。

## 已符合的部分：保留

1. **同一数据库。** `src/server.ts:22` 打开数据库，传给 MCP 的 WorkspaceService
   和网页服务。网页无需另行“同步 Workspace”。
2. **网页以展示为主。** `src/web/views.ts` 呈现统计、申请、时间线和证据；
   当前已授权的少量操作保留，不增加通用编辑台。
3. **有独立手动检查入口。** `src/gmail/router.ts` 的检查接口由登录用户显式触发；
   `src/gmail/checks.ts` 获取邮件，`src/gmail/providers.ts` 调用模型分析，
   再由后台保存。它不唤醒 ChatGPT 定时任务。
4. **有可复用的保存与进度能力。** WorkspaceService 已校验身份、证据并执行幂等保存；
   mail-scan/mail-batch 模块已有持久化回执、分页和处理记录。保留这些能力，
   不能因当前调用失败而删除追踪记录或直接修改业务表。

## 需要调整的部分

### 1. 优先统一邮件身份和跨入口去重

网页在 `src/gmail/checks.ts:92` 使用“Google 账户指纹 + Gmail message ID”；
MCP 在 `src/gmail/mcp-reader.ts:91` 使用“mailbox-1/2 + message ID”。
`src/application/workspace-service.ts` 按申请、provider 和 externalId 查找已有证据。
因此同一邮件经不同入口处理时，可能得到不同 externalId，不能保证跨入口去重。
`src/application/mail-batch-service.ts:168` 还只按槽位前缀匹配证据，网页保存的证据
不能直接满足它的已记录判断。

建议抽取共用来源标识，以稳定账户身份和邮件 ID 为基础，显示用 mailbox 别名另存。
需要兼容既有两种 ID，识别槽位重新绑定，不盲目覆盖、合并或删除历史证据。
这涉及来源身份契约，后续应单独设计兼容处理并测试，不作机械字符串替换。

### 2. 明确手动按钮含义，逐步统一处理规则

现有“检查全部”通过 `applicationCheckTargets()` 枚举已存在的申请；每个申请按
公司/职位搜索，从申请日期前一天开始，并非只查今天早上之后的新增邮件。
申请较多时会重复读取历史邮件和调用模型；它也不能保证发现尚未登记的新申请。

现有网页检查只保存 EMAIL/NOTE 证据，不改变申请生命周期或创建待办。
因此它现在是“补查已有申请的邮件证据”，不是完整每日任务的手动重跑。

建议普通补查优先限定近期增量，保留单个申请的定向检查。
两条入口共用身份解析、证据校验、去重和保存能力；指定申请的检查与全邮箱增量检查
仍应保留各自明确的范围。不能将单申请检查成功写成两个邮箱全量覆盖成功。
网页补查是否也允许登记新申请、自动更新状态或待办，需在实现契约中明确；
本次产品澄清不自动扩大当前网页写入权限。

### 3. 后台统一维护进度，页面准确显示数据时效

MCP 路径使用 mail_scan_runs/checkpoints/streams/batches/processed；
网页路径在进程内 Map 保存活动检查，结束后另写 NOTE 回执。
网页手动运行不会自动推进每日扫描的进度，两个入口没有共用活动任务锁。
数据库事务能保护写入，不代表跨入口只处理一次或完整覆盖。

建议形成共用的进度与重试约定，记录触发来源、查询范围、成功覆盖、部分失败、
待处理项，并对重叠运行去重或排队。保留后台开始/结束记录，逐步减少模型承担
机械进度管理的职责；不要仅把写回执挪到扫描末尾或删除开始回执。

页面已有“上次读取”和扫描进度区域，应统一呈现每日及手动检查的相关时效：
查到什么时候、是否完整、是否有正在执行的补查。“刚刷新页面”不能代表“刚查过邮箱”。

## 执行方式与当前阻塞

上述职责划分不指定必须使用哪一种调度器。现有每日任务在 ChatGPT 中；
改成自有后台定时任务调用模型 API 会改变执行环境、费用及运维责任，不属于本次评估已选定的实现。
现有网页后台模型调用也不等于已具备完整自动入库任务。

当前替代任务仍暂停，尚未实际定时运行。在它所在的对话中，手动创建回执的调用
在允许一次后仍报告平台安全拦截，确切规则未知。
参见 [平台调查记录](../mvp/JOB_TRACKER_PLATFORM_BLOCK_REPORT_2026-09-08.md)。
本评估不以改名、换入口或数据库直写重试该被拦请求；上述结构调整不能被宣称为拦截修复。

## 建议实施顺序与验收

1. 先完成稳定来源标识及历史 ID 兼容设计，统一跨入口去重。
2. 明确按钮的增量范围与业务更新权限，再接入共用保存和进度能力。
3. 校准页面时效与部分失败说明，保留现有展示功能。
4. 平台问题解决后，分别验证真实定时运行、下午补查及网页读取。

关键验收：早上处理过的邮件下午不重复新增；下午的新邮件能被补查保存并显示；
打开网页不触发邮件/模型调用；双入口同时执行或服务重启不丢进度；
只成功查一个邮箱、只查一个申请均不冒充全邮箱扫描成功；新申请与状态/待办更新
符合各入口明确授权和现有生命周期规则。

本次为静态代码与历史证据评估，未更改运行代码、数据库、定时任务或部署；
未重新执行真实邮件检查或安全拦截请求。文档检查不等同于上述运行验收。
