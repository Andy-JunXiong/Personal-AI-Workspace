## Continuity and benefits

- Upstream requirement：[流程评估](../architecture/JOB_TRACKER_FLOW_REVIEW_2026-09-08.md)发现两个入口使用不同邮件标识、网页反复查历史、手动进度依赖进程内存。用户明确授权实施调整。
- Current package：统一新邮件标识和证据去重，网页改为近期增量补查，持久化每个申请的手动检查及成功范围，在同一页面展示每日与手动检查。本地任务指令同时改为使用读取工具返回的确切 externalId。
- Downstream enablement：010 → 011 副本升级和旧镜像回退演练已通过，线上切换与原数据保留核对通过；ChatGPT 定时写入拦截仍需平台解决。
- Short-term benefits：测试证明同一封邮件经两入口或并发保存不会重复新增证据；已存邮件不再重复交给网页模型分析；手动重试能使用持久化范围，失败不推进成功覆盖。
- Long-term benefits：网页维持展示为主，自动与手动入口维护同一份可追溯记录，不引入第二份业务数据库或相互唤醒关系。

## 已实现

### 邮件身份和兼容

- 新增 `gmail/source-identity.ts`，沿用已部署网页的 Google subject SHA-256 前 24 位加 message ID 格式。
- Gmail MCP 读取返回相同 externalId；显示、请求定位和回执仍使用 mailbox-1/2 别名，不暴露账户凭据。
- 分批处理把实际读取的 externalId 存在新附属表中，确认处理时按该值匹配证据，能识别网页保存的记录。
- 每个每日处理槽位绑定稳定账户指纹。换绑后拒绝沿用旧覆盖；读取期间换绑也拒绝消费不一致结果。
- 旧网页指纹记录自然兼容；历史裸 message ID 或 mailbox 前缀没有足够账户归属证据时，保留原记录并报告待核对，不能自动合并或伪称去重成功。
- 010 已有队列/成功覆盖但没有账户绑定时，升级不会猜测账户，恢复处理前需核对归属。生产历史是否仍为空必须在发布前重新查证。

### 网页按需补查

- 保留单申请和全部已有申请入口、现有认证和只读 Gmail 授权。
- 首次按申请查询最近 48 小时；后续从该申请、账户、查询条件的上次成功范围向前重叠 24 小时，最多回看七天。
- 查询包含固定截止时间，并按邮件实际时间过滤，窗口结束之后到达的邮件留给下一次检查。
- 已有证据先在共同保存层查重，直接展示已存摘要；仅未保存的候选邮件交给模型。
- 仍然只写 EMAIL/NOTE 证据，不新增申请、修改生命周期或创建待办。“全部”指全部已有申请，不代表完整邮箱扫描。

### 进度和页面

- 新增申请级持久化手动回执、按账户及查询条件区分的成功覆盖。同一申请的活动运行在数据库内排他，跨处理器重复点击会返回同一运行。
- 完成回执和成功覆盖在同一个事务中提交；一个邮箱失败，不推进该邮箱覆盖。
- 运行超过三分钟仍无完成结果会显示中断；再次启动保留旧记录，从成功范围重试，已保存的证据不会重复新增。
- 今日页将网页补查与每日任务记录一起呈现，但保留范围区分。页面刷新只读数据库，不启动邮件检查。

## 明确的运行边界

这次统一的是来源身份、证据保存规则和可见的持久化进度，不是把两个入口合成同一调度器。
申请级手动范围不推进全邮箱每日 checkpoint。两入口并发保存由共同事务及来源去重保护；
没有新增跨入口的全局任务锁，极端并发仍可能重复进行模型分析。
“检查全部”的批次总进度仍在内存中；每个已启动申请的结果及覆盖已持久化。
进程重启后，用户可再次点击，重新遍历已有申请；系统不声称整个批次会自动后台续跑。
无关邮件的分类结果目前不缓存，重叠窗口可能再次分析它们。

该版本不重放此前被安全检查拦截的调用，不删除开始回执，不将写工具改为只读。
本次经用户“上线吧”授权部署并执行数据库迁移；未改动线上任务或连接权限，并未解决或证明绕过平台安全拦截。
